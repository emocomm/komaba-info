# 駒場情報演習教材:公開鍵暗号とディジタル署名

### 1 教材の目的

公開鍵暗号方式における「公開鍵」と「秘密鍵」の役割を、Web上の演習を通じて体験的に理解させる。学生は自分の鍵ペアを作り、教員の公開鍵で提出本文を暗号化し、自分の秘密鍵で暗号文に署名する。最後に、教員側が学生の公開鍵で署名を検証する流れを確認する。

この教材の中心は、暗号技術の数学的詳細ではなく、次の対応関係を自分で判断できるようにすることである。

- 自分だけが持つもの:秘密鍵
- 他人に渡してよいもの:公開鍵
- 教員宛の本文を暗号化するときに使うもの:教員の公開鍵
- 教員宛の暗号文を復号するときに使うもの:教員の秘密鍵
- 自分が作ったことを示す署名を作るときに使うもの:自分の秘密鍵
- 署名が本人のものか確認するときに使うもの:その人の公開鍵

導入では、次の2点を強調する。

- **秘密鍵は他の人には絶対に共有しない**
- **配るのは公開鍵である**

期末試験で想定される対応は次のとおり。

- E:秘密鍵
- F:公開鍵
- G:ディジタル署名

### 2 学習目標

- 共通鍵暗号と公開鍵暗号の違いを説明できる
- 公開鍵と秘密鍵の違いを、「誰に見せてよいか」という観点で説明できる
- 暗号化の場面で、受信者の公開鍵を使い、受信者の秘密鍵で復号することを説明できる
- 署名の場面で、本人が秘密鍵で署名を作り、相手が公開鍵で検証することを説明できる
- 「共通鍵」「公開鍵」「秘密鍵」「一方向ハッシュ関数」「電子指紋」「ディジタル署名」「認証局」「電子証明書」を、典型的な文脈で区別できる
- 秘密鍵を提出したり共有したりしてはいけない理由を説明できる

### 3 想定される所要時間

- 教室での演習時間:50分
  - 鍵ペア作成、教員宛の暗号化、自分の秘密鍵による署名、LMS提出までを授業内で完了させる。
- 補足説明またはミニレポート:授業内または宿題で15〜20分
  - 期末試験型の穴埋め問題を通じて、公開鍵、秘密鍵、ディジタル署名、認証局、電子証明書の対応を振り返らせる。

### 5 演習の流れ

#### 5.1 授業前に教員が準備すること

1. [鍵ペア作成ツール](../keygen/)で教員用の鍵ペアを作る。
2. 教員の公開鍵 `PUB-...`、公開鍵の指紋 `FP-...`、VisualHostKey風の視覚指紋をスライドに載せる。
3. 教員の秘密鍵 `SEC-...` は手元に保存する。これは学生の暗号文を復号するために使う。

#### 5.2 授業中に学生が行うこと

1. レクチャーページで、共通鍵暗号と公開鍵暗号の違いを確認する。
2. [鍵ペア作成ツール](../keygen/)で自分の鍵ペアを作る。
   - 公開鍵 `PUB-...` は後でLMSに提出する。
   - 秘密鍵 `SEC-...` は署名ツールで使うが、LMSには提出しない。
3. UTOLの課題欄に表示された教員の公開鍵、指紋、VisualHostKey風の視覚指紋を確認する。
4. [期末試験型の穴埋め問題](../exam-practice/)で、読み取った穴埋め文と語群を見ながら、言葉を埋めた文章を作る。
5. [暗号化の手順](../encrypt/)に従って[暗号化ツール](../encrypt-tool/)を開き、教員の公開鍵でその文章を暗号化して暗号文 `CIPHER-...` を作る。
6. [署名の手順](../sign/)に従って[署名ツール](../sign-tool/)を開き、暗号文に自分の秘密鍵で署名して署名 `SIG-...` を作る。
7. LMSの提出テキスト欄に、暗号文、署名、自分の公開鍵が分かるように書いて提出する。

#### 5.3 授業後に教員が行うこと

1. LMSから提出データを出力する。
2. [教師用確認ページ](../teacher/)に、暗号文、署名、学生の公開鍵を読み込ませる。
3. 教員の秘密鍵で暗号文を復号し、穴埋め済み文章とA〜Kの回答を確認する。
4. 学生の公開鍵で署名を検証する。
5. 典型的な誤答を確認する。
   - 自分の公開鍵で教員宛に暗号化している
   - 提出テキストの自分の公開鍵部分に秘密鍵を貼っている
   - 署名作成と暗号化を混同している
   - 検証に秘密鍵を使うと答えている

### 6 LMS提出物

学生には、1つのJSONやファイルを提出させない。LMS側の提出欄は1つだけとし、その中に暗号文、ディジタル署名、自分の公開鍵をラベル付きで書かせる。

LMS提出テキストに含めるもの:

1. **暗号文**
   - 暗号化ツールで作った `CIPHER-...` から始まる文字列
2. **ディジタル署名**
   - 署名ツールで作った `SIG-...` から始まる文字列
3. **自分の公開鍵**
   - 鍵作成ツールで作った `PUB-...` から始まる文字列

提出させないもの:

- 自分の秘密鍵 `SEC-...`
- 学生の公開鍵の指紋
  - 教員側で、提出された公開鍵から計算できる
- 教員の公開鍵の指紋
  - 暗号化ツール内で確認するための情報であり、提出の必須項目ではない
- 教員の公開鍵の視覚指紋
  - 公開鍵確認の補助表示であり、提出の必須項目ではない
- 署名対象
  - 今回は常に暗号文に署名する設計にする
- 提出形式のバージョンやJSON全体
  - LMSの1つのテキスト欄に、人間が読んで分かるラベル付きで3項目を書く
- `student_label`
  - 10桁IDや氏名はLMS側の提出者情報から取得する

学生に表示する提出指示:

```text
LMSの提出欄に、以下の3つを分かるように書いて提出してください。

暗号文:
暗号化ツールで作った CIPHER-... から始まる文字列

ディジタル署名:
署名ツールで作った SIG-... から始まる文字列

自分の公開鍵:
鍵作成ツールで作った PUB-... から始まる文字列

SEC-... から始まる秘密鍵は提出しないでください。
JSONやファイルにまとめる必要はありません。
```

### 7 鍵のモデルと実装方針

#### 7.1 基本方針

教員用と学生用で鍵生成の仕組みを分けない。教員も学生も[鍵ペア作成ツール](../keygen/)で鍵ペアを生成する。学生には「私の鍵」として使わせ、教員は同じページで作った鍵を「教員の鍵」としてスライドに載せる。

- 教員用も学生用も、公開鍵は `PUB-...` と表示する
- 教員用も学生用も、秘密鍵は `SEC-...` と表示する
- 鍵ペアは作成するたびに別のものになる
- 違うのは鍵の使い道だけである

使い道の違い:

| 利用者 | 公開鍵の使い道                 | 秘密鍵の使い道         |
| ------ | ------------------------------ | ---------------------- |
| 教員   | 学生が教員宛の本文を暗号化する | 教員が暗号文を復号する |
| 学生   | 教員が学生の署名を検証する     | 学生が暗号文に署名する |

#### 7.2 学生用鍵の保存

[鍵ペア作成ツール](../keygen/)は、学生ごと、ブラウザごとに別々の鍵ペアを作る。

- 初回アクセス時には鍵ペアを自動生成しない
- 保存済みの鍵ペアがない場合は、「鍵ペアを作る」ボタンを表示する
- 学生が「鍵ペアを作る」ボタンを押したときに鍵ペアを生成し、localStorage に保存する
- 2回目以降のアクセスでは、保存済みの鍵ペアを読み込んで表示する
- 保存済みの鍵ペアがある場合、同じボタンのラベルを「鍵を作り直す」に変える
- 「鍵を作り直す」操作をした場合だけ、新しい鍵ペアを生成して localStorage を更新する
- 別のブラウザ、別の端末、localStorage削除後は別の鍵ペアになる

localStorage のキー名例:

```text
komaba-public-key-20260525-keypair-v1
```

#### 7.3 教員用鍵の作成と保存

教員は授業前に[鍵ペア作成ツール](../keygen/)で鍵ペアを1回作り、公開鍵、指紋、VisualHostKey風の視覚指紋をスライドに載せる。専用の教員用鍵作成ページは作らない。

[鍵ペア作成ツール](../keygen/)には、学生が使う基本表示に加えて、授業準備にも使える保存機能を持たせる。鍵を localStorage に保存するだけでなく、公開鍵と秘密鍵をそれぞれ別のテキストとしてダウンロードできるようにする。

ファイル名例:

```text
komaba-public-key-20260525-public-key.txt
komaba-public-key-20260525-secret-key.txt
```

#### 7.4 内部形式

学生には、常に1組の公開鍵・秘密鍵として見せる。ただし実装上は、必要であれば `PUB-...` と `SEC-...` の中に、暗号化用と署名用の情報をまとめて持たせてよい。

例:

```text
PUB-...
  - 暗号化に使う公開情報
  - 署名検証に使う公開情報
  - 公開鍵の指紋を計算するための情報

SEC-...
  - 復号に使う秘密情報
  - 署名に使う秘密情報
  - 対応する公開鍵の指紋または鍵ID
```

実装は、ブラウザ標準の Web Crypto API を使ってもよいし、授業用のシミュレーションとして実装してもよい。どちらの場合も、画面上の概念は実際の暗号の語法とずれないようにする。

公開鍵の指紋は、公開鍵文字列または公開鍵の正規化データに対してハッシュを計算し、`FP-...` として表示する。

#### 7.5 誤入力検知の方針

学生向けページには、教員の秘密鍵を置かない。テスト実装であっても、学生向けコードに秘密鍵を埋め込むと「秘密鍵は共有しない」という授業の中心メッセージと矛盾する。教員の公開鍵も固定値として埋め込まず、授業スライドに表示されたものを学生が貼り付ける。

ただし、教育的な警告は可能な範囲で出す。`SEC-...` には、対応する公開鍵の指紋または鍵IDのような非秘密情報を含めてよい。暗号化ツールで学生が確認した教員の公開鍵指紋を localStorage に保存しておけば、署名ツールで貼られた `SEC-...` が教員の公開鍵に対応するものかどうかを、秘密鍵そのものをサイトに置かずに判定できる。

ツール側でできる検知は、次の範囲に限定する。

- `PUB-...` と `SEC-...` の形式による鍵種別の判定
- localStorage に保存されている自分の公開鍵・秘密鍵との一致確認
- `PUB-...` と `SEC-...` に同じ鍵ペア由来であることを示す内部IDまたは公開鍵指紋を含め、対応関係を確認する
- 暗号化ツールで確認した教員の公開鍵指紋と、署名欄に貼られた `SEC-...` 内の対応公開鍵指紋を比較する

検知できる例:

- 暗号化用の鍵欄に `SEC-...` が入っている
- 暗号化用の鍵欄に、localStorage に保存されている自分の公開鍵と同じ `PUB-...` が入っている
- 署名用の鍵欄に `PUB-...` が入っている
- 署名用の鍵欄に、暗号化ツールで確認した教員の公開鍵指紋に対応する `SEC-...` が入っている
- 署名用の鍵欄に、localStorage に保存されている自分の秘密鍵と一致しない `SEC-...` が入っている

検知しない例:

- 貼り付けた公開鍵が本当に教員の公開鍵かどうか
  - これはスライドの文字列指紋 `FP-...` と視覚指紋を学生が手動で見比べ、チェックを入れて確認する
- 署名用の鍵欄に入った `SEC-...` の秘密情報本文が「教員の秘密鍵」と完全一致するかどうか
  - 学生向けページは教員の秘密鍵本文を知らないため、秘密鍵そのものとの照合はしない
  - 代わりに、`SEC-...` 内の対応公開鍵指紋が、暗号化ツールで確認した教員の公開鍵指紋と一致する場合に警告する

#### 7.6 VisualHostKey風の視覚指紋

教員の公開鍵確認では、`FP-...` の文字列指紋に加えて、VisualHostKey風のASCIIアートを表示する。これは公開鍵のすり替えに気づきやすくするための補助表示であり、LMS提出項目にはしない。

基本方針:

- 正式な照合には `FP-...` の文字列指紋を使う
- 視覚指紋は、長い公開鍵や指紋を見比べる負担を下げるための補助UIとする
- OpenSSHのVisualHostKeyと完全互換である必要はない
- 同じ公開鍵からは常に同じ見た目が生成され、違う公開鍵では見た目が変わるようにする
- 公開鍵文字列または公開鍵の正規化データのハッシュから、固定サイズの文字グリッドを生成する

表示例:

```text
教員の公開鍵の視覚指紋:
+----------------+
| .  o   .       |
|  + .  o        |
|   * .          |
|  . = . S       |
|     o .        |
+----------------+
```

授業上は、これは「公開鍵の見た目」と説明する。学生は暗号化ツールに教員の公開鍵を貼り付けたあと、スライド上の視覚指紋と、ツールが計算した視覚指紋が同じであることを確認する。

| 場面                 | 使う鍵 | 誰の鍵か | 目的                                       |
| -------------------- | ------ | -------- | ------------------------------------------ |

#### 9.2 [暗号化ツール](../encrypt-tool/)

目的:コマンドラインで `encrypt --key 教員の公開鍵 --in 平文 --out 暗号文` のように行う操作を、WebのGUIで体験する処理専用ツール。ここでは署名は行わず、教員だけが読める暗号文を作るところまでに限定する。

入力:

- 暗号化する本文
  - [期末試験型の穴埋め問題](../exam-practice/)で作成し、[暗号化の手順](../encrypt/)でコピーした「言葉を埋めた文章」を貼り付ける
  - キーワードの一覧だけではなく、空欄を埋めた文章全体にする
- 暗号化に使う鍵
  - 教員がスライドで提示した教員の公開鍵を貼り付ける
  - 貼り付けた鍵から指紋を計算して表示する
  - 貼り付けた鍵からVisualHostKey風の視覚指紋を生成して表示する
- 教員の公開鍵確認チェック
  - `スライドの指紋と見た目を確認しました` というチェックボックス
  - 学生が、ツールに表示された `FP-...` と視覚指紋をスライドの表示と手動で見比べてからチェックする
  - このチェックが入っていない場合は暗号化を実行できない
  - チェックを入れて暗号化した場合は、確認済みの教員の公開鍵指紋を localStorage に保存する

出力:

- 暗号文 `CIPHER-...`
- 暗号文だけをコピーするボタン
- 暗号文を[署名の手順](../sign/)ページへコピーして移すための案内

誤入力時のモーダル:

- 暗号化用の鍵欄に `SEC-...` 形式の秘密鍵が入っている場合
  - `確認してください。ここは「受信者の公開鍵」を入れる欄です。秘密鍵を入れていませんか？`
- 暗号化用の鍵欄に、localStorage に保存されている自分の公開鍵と同じ `PUB-...` が入っている場合
  - `確認してください。教員宛の提出物は教員の公開鍵で暗号化します。自分の公開鍵を入れていませんか？このままだと教員は復号できません。`
- 教員の公開鍵確認チェックが入っていない場合
  - `確認してください。スライドの指紋と、ツールに表示された指紋・見た目を見比べてからチェックを入れてください。`
- 暗号化する本文が空の場合
  - `確認してください。暗号化する本文が空です。穴埋め文に言葉を埋めた文章を作ってから暗号化してください。`

#### 9.3 [署名ツール](../sign-tool/)

目的:コマンドラインで `sign --key 自分の秘密鍵 --in 暗号文 --out 署名` のように行う操作を、WebのGUIで体験する処理専用ツール。暗号化ツールで作った暗号文を読み込み、自分の秘密鍵で署名し、LMSに貼り付ける署名文字列を作る。

入力:

- 署名する対象
  - 暗号化ツールで作った暗号文を貼り付ける
  - 署名対象は平文ではなく暗号文にする
- 署名に使う鍵
  - 自分の秘密鍵を貼り付ける

出力:

- ディジタル署名 `SIG-...`
- 署名対象の確認表示
  - 署名した暗号文の先頭部分を表示し、どの暗号文に対する署名かを学生が確認できるようにする
- 署名をコピーするボタン
  - 学生はこの署名をLMS提出テキストの「ディジタル署名」部分に貼り付ける

誤入力時のモーダル:

- 署名に使う鍵欄に `PUB-...` 形式の公開鍵が入っている場合
  - `確認してください。署名を作る欄には「自分の秘密鍵」を入れます。公開鍵を入れていませんか？`
- 署名に使う鍵欄の `SEC-...` に含まれる対応公開鍵指紋が、暗号化ツールで確認した教員の公開鍵指紋と一致する場合
  - `確認してください。この秘密鍵は、さきほど教員の公開鍵として確認した鍵に対応しているようです。署名には自分の秘密鍵を使います。`
- 署名に使う鍵欄に、localStorage に保存されている自分の秘密鍵と一致しない `SEC-...` が入っている場合
  - `確認してください。署名は「自分の秘密鍵」で作ります。鍵作成ツールで表示されている自分の秘密鍵と違うものを入れていませんか？`
- 暗号文ではなく穴埋め済み文章らしい平文が署名対象に入っている場合
  - `確認してください。今回は暗号化ツールで作った暗号文に署名します。平文を入れていませんか？`
- 署名に使う鍵欄が空の場合
  - `確認してください。署名を作るには自分の秘密鍵が必要です。`
- localStorage に自分の鍵ペアがない場合
  - `確認してください。先に鍵作成ツールで自分の鍵ペアを作ってください。`

署名ツールでは秘密鍵を入力する必要があるため、「秘密鍵を貼ったこと」自体には警告を出さない。ただし、出力欄やLMS提出テキストに秘密鍵を含めない設計にする。

### 10 暗号化する本文

暗号化される本文はJSONである必要はない。学生が[期末試験型の穴埋め問題](../exam-practice/)で作った、言葉を埋めた文章そのものを暗号化する。

```text
盗聴を防ぐための技術として暗号がある。元のデータを平文、暗号化したデータを暗号文といい、暗号文からもとの平文に戻すことを復号という。公開鍵暗号方式では、暗号化と復号のための鍵ペアを作成する。暗号化用の鍵を公開鍵と呼び、復号用の鍵を秘密鍵と呼んで自分だけが所有する。公開鍵を知っている人は誰でも暗号化できるが、それを復号できるのは秘密鍵の所有者である受信者のみとなる。データの改ざん検知に利用できる技術として一方向ハッシュ関数がある。データに一方向ハッシュ関数を適用して得られた計算結果を、データの電子指紋と呼ぶ。送信者が作成したデータの電子指紋を送信者の秘密鍵を用いて暗号化したものがディジタル署名となる。受信者はデータとディジタル署名の双方を受信して、データから作った電子指紋と、ディジタル署名を公開鍵によって復号した電子指紋とを比較する。これらが一致すればデータは確かに秘密鍵の所有者が作成したものであり、改ざんされていないことが確認できる。公開鍵暗号方式の重要な点は、本当に意図した相手の公開鍵であることの保証にある。公開鍵が本当に相手のものかを確認するために、信頼できる第三者である認証局がその公開鍵にディジタル署名をつけることがある。この技術を用いて、Webサーバの公開鍵が本物であることを確認するためのものが電子証明書である。
```

教師側の一括処理では、復号後の文章から、想定正解に対応する語が入っているかを確認する。

### 11 穴埋め問題

読み取った穴埋め文:

```text
盗聴を防ぐための技術として暗号がある。元のデータを[A]、暗号化したデータを暗号文といい、暗号文からもとの[A]に戻すことを[B]という。[C]暗号方式では、暗号化と[B]のための鍵ペアを作成する。暗号化用の鍵を[C]と呼び、[B]用の鍵を[D]と呼んで自分だけが所有する。[C]を知っている人は誰でも暗号化できるが、それを[B]できるのは[D]の所有者である受信者のみとなる。データの改ざん検知に利用できる技術として[E]がある。データに[E]を適用して得られた計算結果を、データの[F]と呼ぶ。送信者が作成したデータの[F]を送信者の[G]を用いて暗号化したものが[H]となる。受信者はデータと[H]の双方を受信して、データから作った[F]と、[H]を[I]によって[B]した[F]とを比較する。これらが一致すればデータは確かに[G]の所有者が作成したものであり、改ざんされていないことが確認できる。[C]暗号方式の重要な点は、本当に意図した相手の[C]であることの保証にある。[C]が本当に相手のものかを確認するために、信頼できる第三者である[J]がその[C]に[H]をつけることがある。この技術を用いて、Webサーバの[C]が本物であることを確認するためのものが[K]である。
```

語群:

```text
共通鍵 (*)、公開鍵 (*)、電子鍵 (*)、秘密鍵 (*)、圧縮、一方向ハッシュ関数、構文、ディジタル署名、電子印鑑、電子指紋、電子証明書、認証局、パスワード、平文、標本化、復号、符号化、DRM、HTTPS、P2P、PKI
```

想定正解:

- A = 平文
- B = 復号
- C = 公開鍵
- D = 秘密鍵
- E = 一方向ハッシュ関数
- F = 電子指紋
- G = 秘密鍵
- H = ディジタル署名
- I = 公開鍵
- J = 認証局
- K = 電子証明書

実装時の注意:

- `公開鍵` と `秘密鍵` は語群では `(*)` 付きなので、2回以上使える
- `秘密鍵` は D と G の両方に入る
- `公開鍵` は C と I の両方に入る
- `[H]をつける` は `ディジタル署名をつける` という形になる
- Webで実際に使われるものとしては、Webサーバの電子証明書はサーバ証明書とも呼ばれる
- 暗号化するのは、正解一覧だけではなく、空欄が埋まった文章全体にする

### 12 学生向け課題文案

今日の課題では、自分の公開鍵と秘密鍵を作り、穴埋め済みの試験文を教員宛に暗号化します。さらに、自分の秘密鍵で暗号文に署名を作り、教員が自分の公開鍵で署名を検証できる形にして提出します。

作業中に特に注意すること:

- 秘密鍵は自分だけが持つ
- 公開鍵は相手に渡してよい
- 教員に読んでほしい本文は、教員の公開鍵で暗号化する
- 自分が本人であることを示すときは、自分の秘密鍵で署名を作る
- 相手は、署名者の公開鍵で署名を検証する

最後に、LMSの提出欄に以下の3つを分かるように書いて提出してください。

```text
暗号文:
CIPHER-...

ディジタル署名:
SIG-...

自分の公開鍵:
PUB-...
```

`CIPHER-...`、`SIG-...`、`PUB-...` の部分は、それぞれ自分がツールで作った文字列に置き換えてください。

`SEC-...` から始まる秘密鍵は提出しないでください。3つの値を1つのJSONやファイルにまとめる必要はありません。

### 13 評価基準

- 公開鍵と秘密鍵の区別ができている
- 教員宛の暗号化に教員の公開鍵を使うと答えられている
- 復号に教員の秘密鍵が必要だと答えられている
- 署名作成に自分の秘密鍵を使うと答えられている
- 署名検証に自分の公開鍵を使うと答えられている
- 期末試験型の穴埋め文で、A〜Kを正しい語に対応させられている
- 秘密鍵を提出しない理由を説明できている

### 14 想定される誤解と教材側の対策

- 誤解:公開鍵は「開ける鍵」、秘密鍵は「閉じる鍵」である
  - 対策:暗号化と署名で役割が変わるため、「誰の鍵か」「公開か秘密か」を表で確認させる。
- 誤解:教員に送るデータは自分の公開鍵で暗号化する
  - 対策:暗号化ツールで「教員は開けません」と警告する。
- 誤解:学生の秘密鍵で本文を処理して公開鍵と一緒に渡せば、教員だけが読める暗号文になる
  - 対策:公開鍵を持つ人なら誰でも読めるため、これは「教員だけが読める暗号化」ではなく署名に近い操作だと説明する。
- 誤解:本人確認では秘密鍵を接続先に送る
  - 対策:署名ツールとLMS提出テキストを分け、送るのは署名と公開鍵であり、秘密鍵そのものではないことを画面上で確認させる。
- 誤解:ディジタル署名はメッセージを隠すためのもの
  - 対策:暗号文と署名を別々の出力として表示し、署名は検証用であると説明する。
- 誤解:公開鍵ならどれでもよい
  - 対策:教員の公開鍵指紋とVisualHostKey風の視覚指紋を確認させ、公開鍵のすり替えを短く扱う。

### 15 実装上の注意

- サイトは静的なJekyllページで実装する。
- レクチャー・手順ページとツールページを分ける。
  - レクチャー・手順ページは順番に進めるナビゲーションを持つ
  - [暗号化の手順](../encrypt/)と[署名の手順](../sign/)は、学生に具体的な手順を示すページにする
  - 処理だけを行うツールページは[暗号化ツール](../encrypt-tool/)と[署名ツール](../sign-tool/)にする
  - ツールページは手順ページから必要な場面で呼び出す
  - 教師用ページは学生向けナビゲーションに載せない
- ツールの状態保存は localStorage でよい。
- [期末試験型の穴埋め問題](../exam-practice/)の入力欄はリアルタイムに localStorage に保存し、ページを移動して戻っても復元する。
- 本物の個人情報や実ファイルを扱わない。入力は授業用の短いテキストに限定する。
- 各ページにコピー用ボタンを置く。
- 暗号化ツールと署名ツールの間は、ファイルではなく暗号文のコピー&ペーストでつなぐ。
- 秘密鍵をコピーする操作には確認表示を入れる。
- 署名ツールは署名文字列だけをテキスト欄に出力し、コピー用ボタンを用意する。
- LMSには、暗号文、ディジタル署名、自分の公開鍵を1つのテキスト欄にラベル付きで提出させる。
- 最終確認ページでは、LMSに貼る提出テキストを確認させる。提出テキストに `SEC-...` が入っている場合は警告する。
- 教師用ページは、LMSから出力した提出テキストから暗号文、ディジタル署名、学生の公開鍵を読み込み、学生の公開鍵から指紋を計算する。
- 教員の公開鍵確認では、文字列指紋 `FP-...` に加えてVisualHostKey風の視覚指紋を表示する。ただし、これは確認補助であり、LMS提出項目にはしない。
- 暗号化ツールでは、教員の公開鍵確認チェックを必須にする。指紋や視覚指紋の一致はツールが自動判定するのではなく、学生がスライドと手動で見比べる。
- 暗号化する本文はJSONにしない。学生が書いた穴埋め済み文章そのものを暗号化する。
- 誤った種類の鍵を入れたときの確認モーダルは必須とする。学生が「どの欄にどの鍵を入れるべきか」を自分で修正できる文言にする。
